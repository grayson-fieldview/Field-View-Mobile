CRITICAL CONTEXT — iOS Registration Storm

Session 30.5 testing on iPhone Dev Build revealed iOS fires "entered" events for ALL newly-registered regions immediately after startGeofencingAsync, BEFORE GPS lock is acquired. The user is physically in West Palm Beach but iOS reported "entered" for projects in Denver, Phoenix, Dallas, Atlanta, AND West Palm Beach simultaneously.

This is documented iOS behavior — when iOS doesn't yet know the device's actual position, it defaults to "treat as inside" for all registered regions. The "outside" determinations come later as GPS acquires real position.

Without explicit handling, the Session 31 handler would fire 5 simultaneous clock-ins to 5 different projects across the country every app launch. UNACCEPTABLE.

Required filtering logic — must be implemented in this session:

1. Verify physical proximity before trusting an "entered" event
   - Use Location.getCurrentPositionAsync() inside the task handler
   - Compute distance from device to project's lat/lng using haversine formula
   - REJECT the event if distance > 200m (geofence radius is 30m, but GPS accuracy varies — 200m gives generous margin while still excluding cross-country false positives)
   - LOG rejected events with: [geofence] rejected: device <distance>m from <project name> (radius 30m)

2. Per-region debounce
   - In-memory Map<regionId, lastClockInTimestamp>
   - REJECT enter events for a region if last clock-in to that region was within the last 5 minutes
   - This handles GPS jitter (entering and re-entering the boundary as accuracy fluctuates)
   - LOG rejected events: [geofence] rejected: <project> debounced (last clock-in <Xm> ago)

3. Already-clocked-in suppression
   - Check if user has any active time entry (existing /api/timesheets/active endpoint)
   - If yes, REJECT the new clock-in attempt
   - LOG: [geofence] rejected: user already clocked in to <project>

ARCHITECTURE — Task Body in Headless JS

The task body runs OUTSIDE React. No useContext, no hooks, no Provider state. Must work with module-level singletons and direct API calls.

Available primitives:
- expo-task-manager TaskManager.defineTask() — already configured at module top in geofencing.ts
- expo-location for getCurrentPositionAsync
- expo-notifications for push notifications (NEEDS INSTALL — flag in diagnosis)
- AsyncStorage for any persistent state needed
- Direct fetch() to API endpoints (services/api.ts uses apiFetch which depends on session cookies)

Authentication question for diagnosis:
- The mobile app uses cookie-based sessions per project memory
- Cookies are stored in iOS NSURLCredentialStorage and shared across React + headless contexts
- BUT: if the user's session has expired, the headless task can't trigger a re-login flow
- Need to handle 401 gracefully: log [geofence] auth failed: session expired, queue for retry on next app foreground
- Do NOT attempt to refresh the session in headless — too complex for v1
