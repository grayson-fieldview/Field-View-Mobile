Session 29: iOS Location Permissions Onboarding for Field View Mobile

CONTEXT
This is Session 29 of the Field View build, kicking off Phase 2 (geofencing for auto clock-in/out). This session is permissions only — no geofencing logic, no project sync, no API calls. The goal is a complete, production-quality iOS location permission flow that we can build on top of in Sessions 30+.

The phone is iPhone-only for v1. Android is deferred to Phase 3.

The full Phase 2 spec is in the project owner's Google Drive (Word doc). I'll paste relevant excerpts inline below so you don't need to ask for it.

LOCKED DECISIONS FROM SPEC (do not deviate)

- Required permission level: "Always Allow" (background geofences need it)
- Two-stage iOS permission flow: "When In Use" first, then "Always" upgrade after first app use
- Pre-prompt screens before EVERY iOS system dialog (industry standard; iOS only shows Always upgrade once, missing it costs us the feature)
- Denial states must show in-app banner with deep-link to Settings to re-enable
- Manual clock-in must continue working unchanged when permission is denied — feature degrades gracefully, never breaks

WHAT TO BUILD

1. New screen: artifacts/mobile/screens/onboarding/LocationPermissionScreen.tsx
   - Full-screen pre-prompt explainer
   - Plain-language copy explaining WHY (not WHAT): "Field View can clock you in and out automatically when you arrive at a job site, so you don't have to remember. To make this work, we need your location even when the app is closed."
   - Visual: simple icon (use lucide-react-native, MapPin or Target icon), title, body paragraph, primary "Continue" button, secondary "Not now" link
   - Match existing app styling (orange primary buttons #F97316 or whatever the existing token is — don't invent new colors, look at the existing Clock In button styling)

2. New service: artifacts/mobile/services/permissions.ts
   - Wraps expo-location's permission APIs
   - Exports a hook: useLocationPermission()
   - Returns: { status, requestForegroundPermission, requestBackgroundPermission, openSettings }
   - Where status is one of: "undetermined" | "foreground-granted" | "always-granted" | "denied" | "restricted"
   - Internally caches the latest permission state and re-checks on AppState change to "active" (user might have toggled in Settings)
   - openSettings uses Linking.openURL("app-settings:") on iOS

3. Permission flow integration:
   - Determine where in the existing app navigation this screen should appear
   - Likely: after login/auth, before main app, IF status === "undetermined" OR ("foreground-granted" AND user hasn't seen the upgrade prompt yet)
   - Once permission is "always-granted" OR explicitly denied, skip this screen entirely
   - DO NOT block the app on denial. User can deny and continue to manual clock-in.

4. Denial banner component: artifacts/mobile/components/LocationPermissionBanner.tsx
   - Renders only when status is "denied" or "foreground-granted" (not full Always)
   - Copy: "Auto clock-in is disabled. Enable location access in Settings to turn it on."
   - Tap action: calls openSettings()
   - Dismissible per-session (state in component, doesn't need to persist)
   - Shows on the main projects/timesheet screens, NOT on the manual clock-in flow itself

5. app.json updates:
   - Add NSLocationWhenInUseUsageDescription string: "Field View uses your location to detect when you arrive at job sites."
   - Add NSLocationAlwaysAndWhenInUseUsageDescription string: "Field View uses your location in the background to automatically clock you in and out at job sites, so you don't have to remember."
   - These strings appear in the iOS system permission dialog. Make them clear and specific — Apple rejects vague ones in App Review.

WHAT NOT TO BUILD IN THIS SESSION

- No project lat/lng fetching
- No clock-in/out triggering
- No push notifications
- No server changes — this is purely mobile
- No new database columns

ACCEPTANCE CRITERIA (from spec)

- Fresh install (or after deleting and re-installing) shows the pre-prompt screen before any iOS system dialog
- Granting "When In Use" → on next app cold-start (or after a real action that needs location), shows second pre-prompt + Always upgrade dialog
- Denying any prompt → app continues to work normally, banner appears on main screens, banner deep-links to Settings
- useLocationPermission() returns correct status across all five values
- AppState change to "active" re-checks permission state (user toggled in Settings → app reflects new state without restart)
- Manual clock-in flow is unchanged and works regardless of permission state
- Both NSLocation*UsageDescription strings present in app.json with the exact copy specified above
