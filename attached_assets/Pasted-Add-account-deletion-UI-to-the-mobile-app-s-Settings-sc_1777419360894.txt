Add account deletion UI to the mobile app's Settings screen. Two flows:

Leave team (for non-owner users) — calls DELETE /api/users/me, signs user out
Delete entire account (for owners only) — calls DELETE /api/account, signs user out

The backend endpoints already exist in production. This prompt is mobile-only.

Step 1: Backend tweak (small) — expose isOwner flag
Before building the mobile UI, the mobile app needs to know if the current user is the account owner. Check the response shape of /api/auth/user — it returns user fields (id, email, role, accountId, etc.) but not an isOwner flag. Mobile currently can't tell ownership from the response.
Action: Skip this step on mobile — flag it as a separate web backend change needed. Mobile will derive ownership by fetching GET /api/account (which already exists per replit.md) and comparing account.ownerId === user.id.
If GET /api/account doesn't exist or doesn't return ownerId, document that as a blocker and stop. Do NOT modify backend code from the mobile project.

Step 2: Find the existing Settings screen
Locate artifacts/mobile/app/settings.tsx or wherever the Settings screen lives (could be inside app/(tabs)/settings.tsx or similar). Read it to understand the existing structure (sections, styling, components used).

Step 3: Add a "Danger Zone" section at the bottom
Below all existing Settings content, add a new section. Visual treatment:

Section header: "Danger Zone" in red (text color: #dc2626 or destructive)
Below the header: visually separated from the rest of settings (extra margin, possibly a thin red border or red-tinted background to make it scannable)
Section sits at the absolute bottom of the scroll view, not in the middle

Inside the Danger Zone, render conditionally:
If user is NOT the owner: Show one button: "Leave team"
If user IS the owner: Show one button: "Delete account" — and add helper text below explaining "This permanently deletes the entire account and all data after a 30-day grace period. To leave the team without deleting the account, transfer ownership first."

Step 4: "Leave team" flow (non-owner)
Tap on "Leave team" button → show a confirmation modal:

Title: "Leave team?"
Body: "You'll lose access to all projects, photos, and data on this team. You can rejoin within 30 days by signing back in. After 30 days, your account will be permanently deleted."
Two buttons: "Cancel" (neutral) and "Leave team" (destructive red)

On confirm:

Call DELETE /api/users/me with body { confirm: true }
On success: sign out the user (call existing signOut from AuthContext), navigate to the login screen, show a toast: "You've left the team. Sign back in within 30 days to restore your access."
On failure: show a toast with the error message, leave the user signed in


Step 5: "Delete account" flow (owner-only)
Tap on "Delete account" → multi-step confirmation:
Modal 1: Initial warning

Title: "Delete account?"
Body: "This permanently deletes the entire account, all projects, all photos, all team members, and your subscription. After 30 days, all data is destroyed and cannot be recovered."
Two buttons: "Cancel" (neutral) and "Continue" (destructive red)

Modal 2: Type DELETE confirmation

Title: "Type DELETE to confirm"
Body: "This action cannot be undone for 30 days. After that, all data is permanently destroyed."
Text input field where user must type "DELETE" (case-sensitive, exactly)
Below the input: a password field (secureTextEntry) labeled "Re-enter your password"
Two buttons: "Cancel" (neutral) and "Delete account" (destructive red, disabled until both fields are filled and confirmText === "DELETE" exactly)

On confirm (button enabled and tapped):

Call DELETE /api/account with body { confirmText: "DELETE", password: <input value> }
On 401 (wrong password): show inline error "Incorrect password" on the password field, stay on modal
On 400 (e.g., type DELETE failed validation): shouldn't happen given client validation, but if it does, show toast with error
On 403 (not owner): shouldn't happen given UI gating, but if it does, show toast and dismiss
On 200 success: sign out, navigate to login, show toast: "Account deleted. Sign in within 30 days to restore."
On network error: show toast, allow retry

Special case for OAuth-only owners (no password set): the backend returns 400 with a message pointing to /forgot-password. Show a different modal: "You need to set a password before deleting the account. Visit field-view.com/forgot-password to set a password, then return here." Do NOT proceed with the deletion flow.

Step 7: Owner detection in Settings screen
When the Settings screen mounts, fetch /api/account once and compare account.ownerId === user.id. Store result in local state. Use this to conditionally render either "Leave team" or "Delete account" button.
Show a loading state while fetching. If the fetch fails (network error), default to showing "Leave team" only (safer — better to under-show options than to incorrectly show "Delete account" to a non-owner who somehow bypassed the check).

Step 8: After deletion, ensure clean sign-out
After either deletion succeeds, the backend invalidates the session (per the deserializeUser gate). The mobile client needs to:

Clear the cookie jar / local auth token (use existing signOut from AuthContext, but verify it actually clears stored credentials — the user shouldn't auto-restore on next launch from cached cookies)
Clear AsyncStorage user data
Navigate to the login screen
Reset any DataContext state (projects, photos, tasks) so the next user signing in doesn't see stale data

Recommend: extend the existing signOut flow rather than building a parallel one. Add a parameter like signOut({ reason: "account_deleted" }) that bypasses the normal "are you sure" UX (since user just confirmed deletion).

Do NOT show pricing or billing info anywhere in the deletion flow
Do NOT add deep links to billing portal or external pages (Apple anti-steering)
Do NOT modify backend code
