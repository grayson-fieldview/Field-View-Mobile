Session 31b: Silent-Auto Clock-in with Notification Receipts

CONTEXT
S31a shipped foreground confirmation banner ("Clock in at X? Yes / Not now") and validated end-to-end in production today including a real-world test at a coffee/ice cream shop. Validated entries visible in manager dashboard with blue "Auto" badge.

Product direction has changed: silent-auto clock-in is now the DEFAULT, not an opt-in. The confirmation banner from S31a is the wrong UX. Refactor it into a post-facto receipt:

- iOS Enter event → filter chain → if accepted, silently call POST /api/timesheets/clock-in with source: "auto_geofence" — NO user confirmation
- After API success, fire a local notification: "You've been clocked in at [Project Name] at 3:15 PM" (or similar — make the copy feel natural)
- Notification tap → deep links to project detail screen where user can review or undo
- Same silent-auto behavior in foreground as background (no UI difference based on app state)

This means S31a's ClockInPromptBanner.tsx is being significantly modified or removed. The module-level emitter pattern + queue infrastructure may still be useful — that depends on diagnosis (see below).

S32 will handle exit symmetrically. S33 may add a user-facing toggle to opt OUT of silent mode (revert to confirmation-required) — flag in S33, not now.

CRITICAL ARCHITECTURAL DECISIONS

1. Notification timing relative to API call:
   - API success → THEN fire notification (current spec, recommended)
   - Race risk: if notification fires BEFORE API completes and API later 500s, user sees "you've been clocked in" but no entry exists
   - Mitigation: await api.clockIn() success, THEN fire notification. If clockIn throws, log error, do NOT fire notification, leave debounce stamp in place to prevent retry storm
   - On 401 (session expired): log [geofence] auth failed: session expired. Do NOT fire notification. Filter 7 (already-clocked-in) won't help here — different failure mode. Do NOT retry from headless context.

2. Notification when foreground vs background:
   - When app is in foreground: use Notifications.scheduleNotificationAsync the same way; iOS handles foreground notification presentation policy via Notifications.setNotificationHandler at app boot. Configure handler to show notification banner + sound even in foreground, OR use a less intrusive in-app toast — your call but recommend just using the OS notification consistently for symmetry
   - When app is in background or killed: same notification call, OS handles delivery
   - The single code path is the same; the behavioral difference is just the OS's handling

3. Deep-link routing target:
   - Existing route: app/project/[id].tsx (project detail screen)
   - For S31b: notification tap should navigate to that route with a query param signaling "show the time entry undo affordance prominently"
   - Suggested: app/project/[id].tsx?recentClockIn=<entry-id>
   - The project detail screen reads the query param on mount; if present, shows a banner/toast at top "Just clocked in at 3:15 PM — tap to undo" with an Undo button that calls clock-out and dismisses
   - This banner/toast lives on the project detail screen, NOT globally — it's a contextual "you got here from a notification" affordance
   - Existing expo-router supports this via useLocalSearchParams() — diagnose current router setup before designing
